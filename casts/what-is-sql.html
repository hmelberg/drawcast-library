What is SQL?

What SQL is, and how one short query keeps just the rows and columns you asked for — and in what order the database does it.

Transcript

SQL is the language we use to ask a database questions — so how does one question pull out just the rows and columns you want?

Take a small table of pets: each row is one animal, each column one fact about it.

Say we want the names and ages of the cats, and nothing else.

In most programming languages you would spell out the steps: go through every row, test it, copy the parts you need.

SQL skips the steps: you describe the result in a query, and the database works out how to get it.

This way of asking is older than it looks: IBM researchers designed SQL in the early 1970s, first calling it SEQUEL.

FROM pets says which table to look in.

Then WHERE species equals cat sets a test that every row must pass.

The database checks each row in turn: Rex is a dog, so out; Misty is a cat, so in.

Three cats pass, the other three rows drop out: WHERE picks the rows.

Now the columns: SELECT name, age says which ones to keep.

Species and owner fall away, and what is left is our answer.

The answer comes back as a table of its own: three names, three ages.

Read the query again, though: you write SELECT first, but it acts last.

In its logic, the database starts at FROM, filters with WHERE, and only then picks the columns.

That order is the whole idea: choose the rows, then the columns, and say what you want, never how.

One last check, on the same table: what does this query give back?

Same table. What does SELECT owner FROM pets WHERE age > 5 give back?

Ana, Dev and Eli: WHERE keeps Rex, Tiger and Coco, and SELECT keeps only their owner column.

So every question you ask a database comes down to two choices: which rows, and which columns.
